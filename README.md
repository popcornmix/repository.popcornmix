# repository.popcornmix

A Kodi add-on repository, served as static files from GitHub Pages at
<https://popcornmix.github.io/repository.popcornmix/>. It carries
[inputstream.airplay](https://github.com/popcornmix/inputstream.airplay), built for each
Kodi release and architecture.

Users install one zip once; Kodi then finds the build matching its own version and
architecture, and keeps the add-on up to date from here.

## For users

Everything they need is on the [landing page](https://popcornmix.github.io/repository.popcornmix/).
In short: download `repository.popcornmix-2.2.1.zip`, turn on *Unknown sources* under
**Settings → System → Add-ons**, install it with **Install from zip file**, then install
AirPlay Receiver from **Install from repository → popcornmix Add-ons**.

## Layout

`docs/` is what GitHub Pages publishes; everything in it except the add-on zips is
generated by `tools/make_repo.py`.

```
docs/
  index.html                                     landing page
  repository/                                    the repository add-on's own index,
    addons.xml                                     so it can update itself in place
    addons.xml.sha256
    repository.popcornmix/
      repository.popcornmix-2.2.1.zip            the zip a user installs
      icon.png, fanart.png
  piers/aarch64/                                 one directory per Kodi release and
    addons.xml                                     architecture (also omega/*)
    addons.xml.sha256
    inputstream.airplay/
      inputstream.airplay-0.1.3.1+piers.aarch64.zip
      icon.png
repository.popcornmix/                           source of the repository add-on
  addon.xml.in                                   @DIRS@ is filled in from what docs/ holds
  icon.png, fanart.png
tools/
  make_repo.py                                   files a zip, regenerates docs/
  build-addons.sh                                builds every target and files the results
```

The zip path Kodi requests is fixed as `<datadir>/<id>/<id>-<version>.zip`, so two builds of
the same add-on and version cannot share a directory. Hence the split by architecture, one
`<dir>` in the repository add-on per directory.

Kodi does not filter `<dir>` entries by architecture — only by its own version, through
`minversion`/`maxversion` — so on, say, an aarch64 box it fetches the x86_64 index too and
discards the entry when it reads its `<platform>`. `make_repo.py` rewrites `<platform>` to
`linux-aarch64`, `linux-x86_64` and so on as it builds each index; the tag inside the add-on's
own zip is empty, which would match everywhere.

`minversion`/`maxversion` are compared against the version of Kodi's `xbmc.addon` pseudo
add-on, which is `ADDON_API` in Kodi's `version.txt`. That trails the Kodi version during a
development cycle: Kodi 22 alphas report `21.90.x` and only the release reports `22.0.0`,
which is why each range starts at the previous major's `.90`.

## Rebuilding

```bash
tools/build-addons.sh --pin v0.1.3 --commit    # then push
```

That is the whole job: for every target it moves LibreELEC's pin to the given tag, builds the
add-on with LibreELEC's buildsystem, files the zip under `docs/`, regenerates the indexes and
the landing page, and commits. `--arch x86_64` and `--series omega` narrow it; without
`--pin` it builds whatever each LibreELEC tree's `package.mk` currently points at.

The add-ons have to be built by LibreELEC, not by a plain cross-compiler, so that they link
against the libraries the image actually ships — the daemon needs `libplist-2.0.so.4` and
`libcrypto.so.3` at runtime, and gets both from Kodi's own dependencies rather than from
anything the zip carries.

Only a pushed commit can be built, because LibreELEC fetches the sources from GitHub rather
than from any checkout — which is as it should be, for a binary published under the GPL.

The targets are LibreELEC's own lowest-common-denominator add-on projects, `Generic`, `ARMv8`
and `ARMv7`, which is what every other project points its users at. This matters more than
it looks: Kodi picks a build by architecture alone, so an aarch64 build made as RPi5 would be
tuned for Cortex-A76, offered to a Cortex-A53 box, and crash on it.

### What a published version says

A published version names the build it is:

```
inputstream.airplay-0.1.3.1+omega.aarch64.zip
                    ~~~~~ ~ ~~~~~ ~~~~~~~
                      |   |   |      architecture
                      |   |   Kodi release
                      |   LibreELEC's PKG_REV
                      the add-on's own version
```

Kodi builds a zip's URL from the add-on id and version alone, so without that tail the six
builds would share three filenames — and `CAddonInstallJob` installs a cached zip of the
right name whatever is inside it. That is not hypothetical: it put a Piers build on a Kodi 21
box, which then failed at instance creation with an incompatible API version.

The tail comes from `PKG_REV`, because LibreELEC composes the version as
`<the add-on's addon.xml version>.<PKG_REV>` and uses `PKG_REV` for nothing else.

Three things about the spelling, all of which fail quietly if got wrong:

- **A dot, never a dash.** `CAddonVersion` treats everything after the *first* dash as the
  revision, so `+omega-aarch64` would leave every architecture comparing equal.
- **The tail goes after LibreELEC's revision.** Kodi's own convention would be
  `0.1.3+omega.1`, but `+` (0x2B) sorts below `.` (0x2E), so that is *less* than a plain
  `0.1.3.1` and no installed copy would ever be offered it.
- **Only `[a-z0-9.+_@~]` survives.** `_` being legal is what lets `x86_64` through. An
  invalid character does not raise an error: the whole version silently becomes `0.0.0`.

### The build trees

`build-addons.sh` builds each Kodi release in its own LibreELEC checkout, kept for this and
nothing else:

| Series | Checkout | LibreELEC |
|---|---|---|
| `piers` | `~/projects/LibreELEC-addons` | master, Kodi 22 |
| `omega` | `~/projects/LibreELEC-addons-12` | `libreelec-12.2`, Kodi 21.3 |

Each is a worktree off the ordinary checkout, with the download cache shared:

```bash
cd ~/projects/LibreELEC.tv
git worktree add --detach ~/projects/LibreELEC-addons-12 upstream/libreelec-12.2
ln -s ~/projects/LibreELEC.tv/sources ~/projects/LibreELEC-addons-12/sources
```

LibreELEC 12 does not carry the add-on, so its tree needs both packages copied in — from
git rather than from a working tree, so no local patches come with them:

```bash
cd ~/projects/LibreELEC.tv
git archive <branch> packages/mediacenter/kodi-binary-addons/inputstream.airplay \
                     packages/addons/addon-depends/inputstream.airplay-depends |
  tar -x -C ~/projects/LibreELEC-addons-12
```

`LE_PIERS` and `LE_OMEGA` point the script somewhere else.

A tree has to hold nothing but LibreELEC and the add-on package. Local patches put something
no user is running into the published binary, and a patch meant for one board stops the other
targets building at all — a Raspberry Pi kernel patch in `packages/linux/patches/` fails to
apply to the mainline kernel that Generic and ARM use, and takes `linux:host` down with it,
which the toolchain needs for its kernel headers. The ordinary working tree is for working in.

### Why a build per Kodi release

The binary interface versions are compiled in, so one build cannot serve both:

| Interface | Kodi 21 Omega | Kodi 22 Piers |
|---|---|---|
| `kodi.binary.global.main` | 2.0.2 | 2.0.3 |
| `kodi.binary.global.filesystem` | 1.1.9 | 1.1.11 |
| `kodi.binary.instance.inputstream` | 3.3.0 | 3.4.0 |

Kodi refuses an add-on whose `<requires>` it cannot satisfy, and the `minversion`/`maxversion`
on each `<dir>` keeps it from ever being offered the wrong one.

Omega has no `INPUTSTREAM_LOW_LATENCY_LIVE`, so the "start mirroring at the live edge"
setting does nothing there. The add-on's CMake detects that with `check_cxx_source_compiles`
rather than assuming, so the same source builds against either.

A rebuild of unchanged sources needs `PKG_REV` bumped in LibreELEC's `package.mk`. The add-on
version is `<its own version>.<PKG_REV>`, so without that the version does not move and Kodi
never offers the update.

To do it by hand instead, `scripts/create_addon` leaves a zip under
`target/addons/<LibreELEC version>/<device>/<arch>/`, and `tools/make_repo.py add <zip>
--series piers --arch aarch64` files it. `make_repo.py build` regenerates without adding
anything — after editing `repository.popcornmix/addon.xml.in`, say — and `build --check`
reports a stale tree instead of writing to it, which is what CI runs.

Pages picks a push up within a minute or so. Kodi rechecks a repository every 24 hours, or on
demand from the add-on's context menu.

## Automating it

`build-addons.sh` is the whole of the work; what is left is deciding what runs it.

The build cannot move to GitHub-hosted runners. LibreELEC builds its own toolchain per
target, from scratch, against tens of gigabytes of sources, and neither the job time limit
nor the 10 GB Actions cache stretches to that. On a machine with the tree already warm a
rebuild is minutes, so the build stays where the tree is and only the trigger is worth
moving.

`.github/workflows/publish.yml` does that: give the build machine a self-hosted runner
labelled `libreelec`, and the workflow builds every target and pushes, either from the
Actions tab with a tag to build, or from a `repository_dispatch` that inputstream.airplay's
own release workflow fires when it tags. Failures land in the Actions tab like any other.

Short of a runner, a cron job on the build machine comparing `git ls-remote --tags` against
LibreELEC's pin does the same with no GitHub setup, at the cost of having nowhere to look
when it breaks. Either way it is the same script, so the ordinary manual run above is the
thing to get right first.

## Adding a Kodi release or an architecture

Add an entry to `SERIES` or `ARCHES` at the top of `tools/make_repo.py`, a row to `TARGETS`
in `tools/build-addons.sh`, and for a new Kodi release an entry in its `TREES`, then build
it. A `<dir>` appears in the repository
add-on only once a directory holds a zip, so
publishing an existing user's first build for a new release requires them to get the new
repository add-on — which is what the self-updating `repository/` directory is for. Bump the
version in `repository.popcornmix/addon.xml.in` whenever its `<dir>` list changes, or
installed copies will never fetch the new one.

## Publishing

GitHub Pages needs turning on once, under **Settings → Pages → Deploy from a branch →
`master` → `/docs`**. The URL baked into the repository add-on is `REPO_URL` in
`tools/make_repo.py`; changing it means bumping the add-on version and re-publishing, and
anyone who installed the old zip keeps pointing at the old URL until they do.

Every zip has a `.sha256` beside it and every `<dir>` declares `<hashes>sha256</hashes>`.
That is what makes Kodi drop whatever it has cached under that name, fetch the file again and
check it; with hashes off it reuses the cached copy unexamined. LibreELEC's own repository can
afford `false` because it serves one build per URL.
