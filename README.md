# repository.popcornmix

A Kodi add-on repository, served as static files from GitHub Pages at
<https://popcornmix.github.io/repository.popcornmix/>. It carries
[inputstream.airplay](https://github.com/popcornmix/inputstream.airplay), built for each
Kodi release and architecture.

Users install one zip once; Kodi then finds the build matching its own version and
architecture, and keeps the add-on up to date from here.

## For users

Everything they need is on the [landing page](https://popcornmix.github.io/repository.popcornmix/).
In short: download `repository.popcornmix-1.0.0.zip`, turn on *Unknown sources* under
**Settings → System → Add-ons**, install it with **Install from zip file**, then install
AirPlay Receiver from **Install from repository → popcornmix Add-ons**.

## Layout

`docs/` is what GitHub Pages publishes; everything in it except the add-on zips is
generated by `tools/make_repo.py`.

```
docs/
  index.html                                     landing page
  repository/                                    the repository add-on's own index,
    addons.xml                                     so it can update itself in place
    addons.xml.sha256
    repository.popcornmix/
      repository.popcornmix-1.0.0.zip            the zip a user installs
      icon.png, fanart.png
  piers/aarch64/                                 one directory per Kodi release and
    addons.xml                                     architecture
    addons.xml.sha256
    inputstream.airplay/
      inputstream.airplay-0.1.2.1.zip
      icon.png
repository.popcornmix/                           source of the repository add-on
  addon.xml.in                                   @DIRS@ is filled in from what docs/ holds
  icon.png, fanart.png
tools/make_repo.py
```

The zip path Kodi requests is fixed as `<datadir>/<id>/<id>-<version>.zip`, so two builds of
the same add-on and version cannot share a directory. Hence the split by architecture, one
`<dir>` in the repository add-on per directory.

Kodi does not filter `<dir>` entries by architecture — only by its own version, through
`minversion`/`maxversion` — so on, say, an aarch64 box it fetches the x86_64 index too and
discards the entry when it reads its `<platform>`. `make_repo.py` rewrites `<platform>` to
`linux-aarch64`, `linux-x86_64` and so on as it builds each index; the tag inside the add-on's
own zip is empty, which would match everywhere.

`minversion`/`maxversion` are compared against the version of Kodi's `xbmc.addon` pseudo
add-on, which is `ADDON_API` in Kodi's `version.txt`. That trails the Kodi version during a
development cycle: Kodi 22 alphas report `21.90.x` and only the release reports `22.0.0`,
which is why each range starts at the previous major's `.90`.

## Adding a build

Build the add-on with LibreELEC's buildsystem, so it links against the same libraries as the
image it will run on:

```bash
cd ~/projects/LibreELEC.tv
PROJECT=RPi DEVICE=RPi5 ARCH=aarch64 scripts/create_addon inputstream.airplay
```

which leaves the zip under `target/addons/<LibreELEC version>/<project>/<arch>/`. Then:

```bash
cd ~/projects/repository.popcornmix
tools/make_repo.py add \
  ~/projects/LibreELEC.tv/target/addons/12.80.7/RPi5/aarch64/inputstream.airplay/inputstream.airplay-0.1.2.1.zip \
  --series piers --arch aarch64
git add -A docs && git commit && git push
```

`add` files the zip, pulls the artwork and changelog out of it to sit beside it, drops any
older version of that add-on, and regenerates everything. Pages picks the change up within a
minute or so of the push; Kodi rechecks a repository every 24 hours, or on demand from the
add-on's context menu.

Kodi cannot tell one LibreELEC project from another, so a single aarch64 build serves RPi4,
RPi5, Amlogic and the rest on that Kodi release. Build it against the oldest LibreELEC
release of that series you intend to support.

`tools/make_repo.py build` regenerates without adding anything — after editing
`repository.popcornmix/addon.xml.in`, for instance. `build --check` reports a stale tree
instead of writing to it, which is what CI runs.

## Adding a Kodi release or an architecture

Add an entry to `SERIES` or `ARCHES` at the top of `tools/make_repo.py`, then `add` a build
for it. A `<dir>` appears in the repository add-on only once a directory holds a zip, so
publishing an existing user's first build for a new release requires them to get the new
repository add-on — which is what the self-updating `repository/` directory is for. Bump the
version in `repository.popcornmix/addon.xml.in` whenever its `<dir>` list changes, or
installed copies will never fetch the new one.

## Publishing

GitHub Pages needs turning on once, under **Settings → Pages → Deploy from a branch →
`master` → `/docs`**. The URL baked into the repository add-on is `REPO_URL` in
`tools/make_repo.py`; changing it means bumping the add-on version and re-publishing, and
anyone who installed the old zip keeps pointing at the old URL until they do.

There are no hashes on the add-on zips (`<hashes>false</hashes>`, as LibreELEC's own
repository has it). The index is covered by `addons.xml.sha256`, and both are fetched over
HTTPS.
